# 12因素代理 - 构建可靠的LLM应用程序的原则

## 项目概述

这个GitHub项目是由Dex创建的，旨在提供构建可靠、可扩展且易于维护的LLM（大型语言模型）应用程序的原则和最佳实践。项目的灵感来源于著名的[12因素应用](https://12factor.net/)方法论，并将其应用于AI代理（Agents）开发领域。

作者Dex在尝试了市场上各种代理框架后，发现许多标榜自己为"AI代理"的产品实际上并不那么"代理化"。许多产品主要是确定性代码，仅在特定位置使用LLM步骤来提供魔法般的体验。因此，作者提出了一个问题：

> ### **我们可以使用哪些原则来构建足够好的LLM驱动软件，以便交付给生产环境中的客户？**

这个项目正是对这个问题的回答，提出了12个因素作为构建可靠LLM应用的指导原则。

## 软件发展简史

### 60年前
软件本质上是一个有向图（Directed Graph）。这就是为什么我们过去常用流程图来表示程序。

### 20年前
DAG（有向无环图）协调器开始流行，如Airflow、Prefect等。这些遵循相同的图形模式，但增加了可观察性、模块化、重试和管理等优势。

### 10-15年前
当ML模型开始变得足够好时，我们看到了带有ML模型的DAG。例如，"将这个列中的文本总结到新列中"或"按严重性或情感对支持问题进行分类"。但归根结底，它仍然主要是相同的确定性软件。

### 代理的承诺
代理（Agents）的最大优势是你可以不再需要预先定义完整的DAG。不需要软件工程师编写每个步骤和边缘情况，你可以给代理一个目标和一组可能的转换，让LLM实时决定路径。

这里的承诺是你可以编写更少的软件，你只需给LLM提供图的"边"，让它找出"节点"。你可以从错误中恢复，编写更少的代码，并且可能发现LLM能够找到问题的新颖解决方案。

### 代理作为循环
代理可以被视为一个包含3个步骤的循环：
1. LLM确定工作流中的下一步，输出结构化JSON（"工具调用"）
2. 确定性代码执行该步骤
3. 将结果反馈回LLM，重复步骤1

## 12因素

### 因素1：自然语言到工具调用

代理构建中最常见的模式之一是将自然语言转换为结构化工具调用。这是一种强大的模式，允许你构建能够推理任务并执行它们的代理。

例如，将一个短语：
> 能否为Terri创建一个750美元的付款链接，用于赞助2月份的AI修补者聚会？

转换为描述Stripe API调用的结构化对象：

```json
{
  "function": {
    "name": "create_payment_link",
    "parameters": {
      "amount": 750,
      "customer": "cust_128934ddasf9",
      "product": "prod_8675309",
      "price": "prc_09874329fds",
      "quantity": 1,
      "memo": "嗨Jeff - 请参阅下面2月份AI修补者聚会的付款链接"
    }
  }
}
```

从那里，确定性代码可以获取payload并对其进行处理。

### 因素2：掌控你的提示词

提示词（Prompts）是LLM输入的关键部分，需要谨慎设计和管理。要创建可靠的代理，你需要完全控制提供给模型的提示词，而不是将其委托给第三方库或服务。

不要将提示工程外包给框架。一些框架提供了"黑盒"方法，例如：

```python
agent = Agent(
  role="...",
  goal="...",
  personality="...",
  tools=[tool1, tool2, tool3]
)

task = Task(
  instructions="...",
  expected_output=OutputModel
)

result = agent.run(task)
```

这对于快速上手很有帮助，但通常很难调优和/或逆向工程以获得精确的结果。相反，将提示词视为一等公民的代码：

```rust
function DetermineNextStep(thread: string) -> DoneForNow | ListGitTags | DeployBackend | DeployFrontend | RequestMoreInformation {
  prompt #"
    {{ _.role("system") }}
    
    你是一个帮助管理前端和后端系统部署的助手。
    你努力确保遵循最佳实践和正确的部署程序，以实现安全和成功的部署。
    
    在部署任何系统之前，你应该检查：
    - 部署环境（暂存与生产）
    - 正确的标签/版本进行部署
    - 当前系统状态
    
    你可以使用deploy_backend、deploy_frontend和check_deployment_status等工具来管理部署。
    对于敏感部署，使用request_approval获取批准。
  "#
}
```
### 因素3：掌控你的上下文窗口

上下文窗口是LLM用来生成响应的文本片段。掌控上下文窗口意味着你需要决定什么内容应该被包含在上下文中，以及如何组织这些内容。

你不一定需要使用标准的基于消息的格式来向LLM传达上下文。

> #### 在任何给定时刻，你对代理中LLM的输入是"这是到目前为止发生的事情，下一步是什么"

一切都是上下文工程。LLM是将输入转换为输出的无状态函数。要获得最佳输出，你需要给它们最佳输入。

创建优秀的上下文意味着：

- 你给模型的提示和指令
- 你检索的任何文档或外部数据（例如RAG）
- 任何过去的状态、工具调用、结果或其他历史
- 来自相关但独立的历史/对话的任何过去消息或事件（记忆）
- 关于输出什么样的结构化数据的指令

在12因素代理发布约2个月后，上下文工程开始成为一个相当流行的术语。这个指南都是关于如何尽可能地利用当今的模型。值得注意的是，未提及的是：

- 对模型参数的更改，如温度、top_p、频率惩罚、存在惩罚等。
- 训练你自己的完成或嵌入模型
- 微调现有模型

我不知道向LLM传递上下文的最佳方式是什么，但我知道你需要灵活性来尝试一切。

### 因素4：工具只是结构化输出

工具调用实际上只是结构化输出。你可以通过指导LLM生成特定格式的输出来实现工具调用，而不需要复杂的框架。

工具不需要复杂。在其核心，它们只是你的LLM的结构化输出，触发确定性代码。

例如，假设你有两个工具`CreateIssue`和`SearchIssues`。要让LLM"使用几个工具中的一个"只是要求它输出我们可以解析为表示这些工具的对象的JSON。

```python
class Issue:
  title: str
  description: str
  team_id: str
  assignee_id: str

class CreateIssue:
  intent: "create_issue"
  issue: Issue

class SearchIssues:
  intent: "search_issues"
  query: str
  what_youre_looking_for: str
```

这种模式很简单：
1. LLM输出结构化JSON
2. 确定性代码执行适当的操作（如调用外部API）
3. 捕获结果并反馈到上下文中

这在LLM的决策和你的应用程序的行动之间创建了清晰的分离。LLM决定做什么，但你的代码控制如何做。仅仅因为LLM"调用了一个工具"并不意味着你必须每次都以相同的方式执行特定的相应函数。

关于"普通提示"与"工具调用"与"JSON模式"以及每种方法的性能权衡，已经有很多讨论。"下一步"可能不像"运行纯函数并返回结果"那样原子化。当你将"工具调用"视为模型输出描述确定性代码应该做什么的JSON时，你会解锁很多灵活性。

#### 更深层的统一：Agent即函数

从更抽象的角度来看，我们可以将Agent和函数调用视为同等地位的操作。本质上，两者都是将输入（一个或多个）转换为输出的过程：

- **传统函数调用**：`function(input) -> output`
- **Agent调用**：`agent(context, query) -> response`
- **工具调用**：`tool(parameters) -> result`

这种统一的视角带来了几个有趣的洞察：

```python
# 传统函数调用
result = calculate_sum(a, b)

# Agent作为函数
response = agent_function(
    context="用户购买历史和偏好", 
    query="推荐适合的产品"
)

# 工具调用
api_result = stripe_tool({
    "action": "create_payment",
    "amount": 100
})

# 统一接口
class UnifiedCall:
    def execute(self, inputs) -> output:
        # 可以是函数、Agent或工具调用
        pass
```

这种统一性让我们能够：

1. **组合性**：将Agent和函数调用无缝组合在更大的工作流中
2. **可替换性**：在某些场景下，传统函数和Agent可以互相替换
3. **标准化接口**：使用相同的调用约定和错误处理机制
4. **递归组合**：Agent可以调用其他Agent，就像函数调用函数一样

```python
# Agent调用链的统一表示
pipeline = [
    ("data_extraction_agent", {"source": "database"}),
    ("analysis_function", {"method": "statistical"}),
    ("summarization_agent", {"style": "executive"}),
    ("formatting_tool", {"output": "pdf"})
]

# 统一执行
result = execute_pipeline(pipeline, initial_input)
```

这种抽象还揭示了一个重要原则：**计算的本质是变换**。无论是确定性的函数还是概率性的Agent，它们都在执行某种形式的信息变换。认识到这一点，我们可以构建更加灵活和可组合的系统。

### 因素5：统一执行状态和业务状态

将代理的执行状态（当前正在做什么）与业务状态（已经完成了什么）统一起来，可以简化设计并提高可靠性。

即使在AI世界之外，许多基础设施系统也试图将"执行状态"与"业务状态"分开。对于AI应用，这可能涉及复杂的抽象来跟踪当前步骤、下一步、等待状态、重试计数等内容。这种分离创造了可能有价值但对你的用例来说可能过度的复杂性。

更明确地说：

- **执行状态**：当前步骤、下一步、等待状态、重试计数等。
- **业务状态**：代理工作流程中到目前为止发生的事情（例如OpenAI消息列表、工具调用和结果列表等）。

如果可能，简化 - 尽可能统一这些状态。

实际上，你可以设计你的应用程序，使得你可以从上下文窗口中推断出所有执行状态。在许多情况下，执行状态（当前步骤、等待状态等）只是关于到目前为止发生的事情的元数据。

你可能有一些不能进入上下文窗口的内容，如会话ID、密码上下文等，但你的目标应该是最小化这些内容。

这种方法有几个好处：

1. **简单性**：所有状态的单一真相来源
2. **序列化**：线程可以轻松序列化/反序列化
3. **调试**：整个历史记录在一个地方可见
4. **灵活性**：只需添加新的事件类型即可轻松添加新状态
5. **恢复**：只需加载线程即可从任何点恢复
6. **分叉**：通过将线程的某个子集复制到新的上下文/状态ID中，可以在任何点分叉线程
7. **人类界面和可观察性**：轻松将线程转换为人类可读的markdown或丰富的Web应用UI

### 因素6：使用简单API启动/暂停/恢复

设计简单的API来控制代理的生命周期，使其能够轻松启动、暂停和恢复操作。

代理只是程序，我们对如何启动、查询、恢复和停止它们有一定的期望。

应该让用户、应用程序、管道和其他代理能够通过简单的API轻松启动代理。

代理及其编排确定性代码应该能够在需要长时间运行的操作时暂停代理。

像webhook这样的外部触发器应该使代理能够从它们离开的地方恢复，而无需与代理编排器进行深度集成。

这与[因素5 - 统一执行状态和业务状态]和[因素8 - 掌控你的控制流]密切相关，但可以独立实现。

注意 - 通常AI编排器将允许暂停和恢复，但不是在工具选择和工具执行之间的时刻。另请参阅[因素7 - 使用工具调用联系人类]和[因素11 - 从任何地方触发，在用户所在的地方与他们会面]。

### 因素7：使用工具调用联系人类

在代理需要人类干预时，使用结构化的工具调用而不是自然语言输出来请求帮助。

默认情况下，LLM API依赖于一个基本的高风险令牌选择：我们是返回纯文本内容，还是返回结构化数据？

你在第一个令牌的选择上投入了很多权重，在"the weather in tokyo"的情况下，是"the"，但在"fetch_weather"的情况下，它是一些特殊的令牌来表示JSON对象的开始。

你可能通过让LLM始终输出JSON，然后用一些自然语言令牌如"request_human_input"或"done_for_now"来声明其意图（而不是"适当的"工具如"check_weather_in_city"）获得更好的结果。

```python
class Options:
  urgency: Literal["low", "medium", "high"]
  format: Literal["free_text", "yes_no", "multiple_choice"]
  choices: List[str]

# 人类交互的工具定义
class RequestHumanInput:
  intent: "request_human_input"
  question: str
  context: str
  options: Options

# 在代理循环中的示例用法
if nextStep.intent == 'request_human_input':
  thread.events.append({
    type: 'human_input_requested',
    data: nextStep
  })
  thread_id = await save_state(thread)
  await notify_human(nextStep, thread_id)
  return # 中断循环并等待带有线程ID的响应返回
else:
  # ... 其他情况
```

你可能没有从这种方法中获得任何性能提升，但你应该进行实验，并确保你可以自由尝试各种奇怪的方法以获得最佳结果。

### 因素8：掌控你的控制流

不要让LLM决定复杂的控制流程。相反，使用确定性代码来处理分支逻辑，而让LLM专注于生成下一步行动的建议。

如果你掌控你的控制流，你可以做很多有趣的事情。

构建适合你特定用例的自己的控制结构。具体来说，某些类型的工具调用可能是打破循环并等待来自人类或另一个长时间运行的任务（如训练管道）的响应的理由。你可能还想合并以下自定义实现：

- 工具调用结果的摘要或缓存
- 对结构化输出的LLM作为评判
- 上下文窗口压缩或其他内存管理
- 日志记录、跟踪和度量
- 客户端速率限制
- 持久睡眠/暂停/"等待事件"

下面的示例展示了三种可能的控制流模式：

- request_clarification：模型要求更多信息，中断循环并等待来自人类的响应
- fetch_git_tags：模型要求git标签列表，获取标签，附加到上下文窗口，并直接传回模型
- deploy_backend：模型要求部署后端，这是一个高风险的事情，所以中断循环并等待人类批准

```python
def handle_next_step(thread: Thread):

  while True:
    next_step = await determine_next_step(thread_to_prompt(thread))
    
    # 为了清晰内联 - 实际上你可以把这个放在一个方法中，
    # 使用异常进行控制流，或者任何你想要的
    if next_step.intent == 'request_clarification':
      thread.events.append({
        type: 'request_clarification',
          data: nextStep,
        })

      await send_message_to_human(next_step)
      await db.save_thread(thread)
      # 异步步骤 - 中断循环，我们稍后会收到webhook
      break
    elif next_step.intent == 'fetch_open_issues':
      thread.events.append({
        type: 'fetch_open_issues',
        data: next_step,
      })
```

### 因素9：将错误压缩进上下文窗口

当出现错误时，以紧凑的方式将其纳入上下文窗口，而不是丢失历史或使窗口溢出。

这个因素虽然有点简短，但值得一提。代理的好处之一是"自我修复" - 对于短期任务，LLM可能会调用一个失败的工具。好的LLM有相当好的机会阅读错误消息或堆栈跟踪，并找出在后续工具调用中需要更改的内容。

大多数框架都实现了这一点，但你可以在不做其他11个因素的情况下只做这一点。这里有一个例子：

```python
thread = {"events": [initial_message]}

while True:
  next_step = await determine_next_step(thread_to_prompt(thread))
  thread["events"].append({
    "type": next_step.intent,
    "data": next_step,
  })
  try:
    result = await handle_next_step(thread, next_step) # 我们的switch语句
  except Exception as e:
    # 如果我们得到一个错误，我们可以将其添加到上下文窗口并再次尝试
    thread["events"].append({
      "type": 'error',
      "data": format_error(e),
    })
    # 循环，或者做其他什么来尝试恢复
```

你可能想为特定的工具调用实现一个错误计数器，以限制单个工具的尝试次数约为3次，或者其他适合你的用例的逻辑。

```python
consecutive_errors = 0

while True:

  # ... 现有代码 ...

  try:
    result = await handle_next_step(thread, next_step)
    thread["events"].append({
      "type": next_step.intent + '_result',
      data: result,
    })
    # 成功！重置错误计数器
    consecutive_errors = 0
  except Exception as e:
    consecutive_errors += 1
    if consecutive_errors < 3:
        # 继续尝试
```

### 因素10：小型、专注的代理

构建小型、专注的代理，而不是试图创建一个可以做所有事情的超级代理。每个代理应该有明确定义的范围和职责。

与其构建试图做所有事情的单体代理，不如构建做一件事情做得好的小型、专注的代理。代理只是更大的、主要是确定性系统中的一个构建块。

这里的关键洞察是关于LLM的限制：任务越大、越复杂，所需步骤就越多，这意味着更长的上下文窗口。随着上下文的增长，LLM更容易迷失或失去焦点。通过让代理专注于特定领域，最多3-10步，也许最多20步，我们保持上下文窗口可管理，LLM性能高。

> #### 随着上下文的增长，LLM更容易迷失或失去焦点

小型、专注的代理的好处：

1. **可管理的上下文**：较小的上下文窗口意味着更好的LLM性能
2. **明确的职责**：每个代理都有明确定义的范围和目的
3. **更好的可靠性**：在复杂工作流程中迷失的可能性较小
4. **更容易测试**：更简单地测试和验证特定功能
5. **改进的调试**：当问题发生时，更容易识别和修复

### 如果LLM变得更聪明怎么办？

如果LLM足够聪明，能够处理100多步的工作流程，我们还需要这个吗？

简而言之，是的。随着代理和LLM的改进，它们**可能**自然地扩展到能够处理更长的上下文窗口。这意味着处理更大DAG的更多部分。这种小型、专注的方法确保你今天就能获得结果，同时准备随着LLM上下文窗口变得更可靠而慢慢扩展代理范围。（如果你以前重构过大型确定性代码库，你现在可能正在点头）。

有意识地控制代理的大小/范围，并且只以允许你保持质量的方式增长，这是关键。正如构建NotebookLM的团队所说：

> 对我来说，AI构建中最神奇的时刻总是当我真正、真正、真正接近模型能力的边缘时出现的

无论这个边界在哪里，如果你能找到这个边界并持续做对，你就会构建神奇的体验。这里有很多护城河可以建立，但像往常一样，它们需要一些工程严谨性。

### 因素11：从任何地方触发，在用户所在的地方与他们会面

设计代理，使其能够从多个入口点触发，并在用户首选的平台或渠道上与他们互动。

如果你已经实现了[因素6 - 使用简单API启动/暂停/恢复]和[因素7 - 使用工具调用联系人类]，你就可以很好地融入这个因素。

让用户能够从slack、email、sms或任何其他他们想要的渠道触发代理。让代理能够通过相同的渠道响应。

好处：

- **在用户所在的地方与他们会面**：这有助于你构建感觉像真人，或至少像数字同事的AI应用
- **外循环代理**：允许代理被非人类触发，例如事件、定时任务、故障等。当他们到达关键点时，可以联系人工寻求帮助、反馈或批准
- **高风险工具**：如果你能快速引入各种人类，你可以让代理访问更高风险的操作，如发送外部邮件、更新生产数据等。保持清晰的标准可以让你获得可审计性和对代理执行更大更好任务的信心

### 因素12：将你的代理设计为无状态的归约器

设计代理为无状态的归约器，它接收当前状态和一个动作，然后返回新状态。这简化了扩展和错误处理。

这是一个更多是为了乐趣的因素，但也有实际价值。将你的代理视为一个无状态的函数，它接收当前状态和一个动作，然后返回新的状态。这种方法使代理更易于测试、扩展和维护。

代理可以被视为一个折叠（fold）或归约（reduce）操作，它将一系列的事件或动作归约成一个最终状态。这种函数式编程概念适用于代理设计，可以使系统更加可预测和可靠。

## 结论

12因素代理方法提供了一个框架，用于构建可靠、可扩展且易于维护的LLM应用程序。即使LLM变得更加强大，这些核心工程技术仍将使LLM驱动的软件更加可靠、可扩展和易于维护。

### 统一计算的未来愿景

随着我们对Agent和传统编程模式理解的深入，一个更加统一的计算范式正在显现。在这个范式中：

- **所有计算都是变换**：无论是确定性函数、概率性Agent，还是混合系统，它们都在执行输入到输出的变换
- **接口标准化**：通过统一的调用约定，我们可以无缝地组合不同类型的计算单元
- **智能分层**：在适当的抽象层次使用适当的工具——用确定性代码处理精确计算，用Agent处理需要推理的任务

这种统一性不仅仅是理论上的优雅，它还带来了实际的工程价值：

1. **更简单的架构**：减少不同组件间的阻抗不匹配
2. **更好的可测试性**：统一的接口使得测试策略更加一致
3. **更强的可组合性**：可以更自由地重新组织和优化计算流程
4. **更清晰的抽象**：帮助开发者更好地思考系统设计

在这个愿景中，12因素代理不仅仅是构建AI应用的指南，更是迈向更加统一、优雅的计算模式的重要一步。
