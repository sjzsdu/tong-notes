# A2A技术实现详解

本文档详细介绍了Agent2Agent (A2A) 协议的核心技术实现，包括任务生命周期管理、流式传输与异步操作，以及代理发现机制。

## 1. 任务生命周期管理

当向代理发送消息时，它可以选择回复：

- 无状态的 `Message`
- 有状态的 `Task`，随后是零个或多个 `TaskStatusUpdateEvent` 或 `TaskArtifactUpdateEvent`

如果响应是 `Message`，则交互完成。如果响应是 `Task`，则任务将由代理处理，直到它处于中断状态（`input-required` 或 `auth-required`）或终端状态（`completed`、`cancelled`、`rejected` 或 `failed`）。

### 1.1 上下文管理

`contextId` 逻辑上组成许多 `Task` 对象和独立的 `Message` 对象。如果A2A代理内部使用LLM，它可以利用 `contextId` 来管理LLM上下文。

对于第一条消息，代理响应服务器生成的 `contextId`。如果代理创建任务，它还将包括服务器生成的 `taskId`。后续客户端消息可以包括相同的 `contextId` 以继续交互，并可选择包括 `taskId` 以继续特定任务。

`contextId` 允许在目标上进行协作或在多个任务之间共享单个上下文会话。

### 1.2 代理响应策略

消息可用于不需要长时间运行处理或协作的简单交互。代理可以使用消息来协商接受任务。一旦代理将传入消息的意图映射到支持的能力，它就可以用 `Task` 回复。

因此，概念上可以有三个级别的代理：

1. **简单代理**：始终仅响应 `Message` 对象的代理。不进行复杂的状态管理，没有长时间运行的执行，并使用contextID将消息绑定在一起。代理很可能直接围绕LLM调用和简单工具进行包装。

2. **任务代理**：生成 `Task`，进行更实质性的工作，可以跟踪并在延长的生命周期内运行。

3. **混合代理**：生成 `Message` 和 `Task` 对象。使用消息协商代理能力和任务的工作范围。然后发送 `Task` 对象以跟踪其执行并在任务状态上协作，如需要更多输入、错误处理等。

代理可以选择始终回复 `Task` 对象，并将简单响应建模为处于 `completed` 状态的任务。

### 1.3 任务改进和后续

客户端可能希望根据任务的结果进行新的询问，和/或改进任务结果。这可以通过使用与原始任务相同的 `contextId` 开始另一个交互来建模。客户端可以通过在 `Message` 对象中使用 `referenceTaskIds` 提供对原始任务的引用来进一步提示代理。

一旦任务达到终端状态（`completed`、`cancelled`、`rejected` 或 `failed`），就无法重新启动。这提供了：

- **任务不变性**：客户端可以可靠地引用任务及其关联的状态、工件和消息
- **清晰的工作单元**：每个新请求、改进或后续都成为一个不同的任务
- **更容易实现**：对代理开发者没有歧义

#### 并行后续

通过让代理为在相同 `contextId` 内发送的每个后续消息创建不同的并行任务来支持并行工作。例如：

```
任务1：预订到赫尔辛基的航班。
（任务1完成后）
任务2：基于任务1，预订酒店。
任务3：基于任务1，预订雪地摩托活动。
```

#### 引用先前的工件

服务代理负责从引用的任务或从 `contextId` 推断相关工件。如果存在歧义，代理将通过返回 `input-required` 状态向客户端请求澄清。

## 2. 流式传输和异步操作

A2A协议为管理可能不会立即完成的异步交互提供了强大的机制，确保客户端能够有效地接收更新。

### 2.1 服务器发送事件（SSE）流式传输

对于产生增量结果或提供持续状态更新的任务，A2A使用服务器发送事件（SSE）支持实时通信。

**关键特征：**

- **发起**：客户端使用 `message/stream` RPC方法发送初始消息并同时订阅该任务的更新
- **服务器能力**：A2A服务器必须通过在其代理卡片中设置 `capabilities.streaming: true` 来表明其对流式传输的支持
- **连接管理**：如果订阅成功，服务器响应HTTP `200 OK` 状态和 `Content-Type: text/event-stream`
- **事件结构**：服务器通过此流发送事件，每个事件的 `data` 字段包含JSON-RPC 2.0响应对象

**事件类型：**

- `Task`：表示A2A服务器为A2A客户端处理的有状态工作单元
- `TaskStatusUpdateEvent`：传达任务生命周期状态的变化，可以提供来自代理的中间消息
- `TaskArtifactUpdateEvent`：交付任务生成的新的或更新的工件，支持块式流式传输

**流终止**：服务器通过在 `TaskStatusUpdateEvent` 中设置 `final: true` 来表示特定交互周期更新的结束。

**重新订阅**：如果客户端的SSE连接意外中断，客户端可以使用 `tasks/resubscribe` RPC方法重新连接到流。

**适用场景：**
- 长时间运行任务的实时进度监控
- 逐步接收大结果（工件）
- 交互式、对话式交换
- 需要来自代理的低延迟更新的应用程序

### 2.2 推送通知机制

对于非常长时间运行的任务或当客户端无法维持持久连接时，A2A通过推送通知支持异步更新。

**配置要求：**

- **服务器能力**：A2A服务器必须通过在其代理卡片中设置 `capabilities.pushNotifications: true` 来表明支持
- **配置提供**：客户端向服务器提供 `PushNotificationConfig`，包括：
  - `url`：webhook URL
  - `token`（可选）：客户端生成的验证令牌
  - `authentication`（可选）：身份验证要求

**通知流程：**

1. A2A服务器在任务达到重要状态变化时发送推送通知
2. 通知包含足够信息让客户端识别任务ID和更新性质
3. 客户端收到通知后使用 `tasks/get` RPC方法检索完整的更新Task对象

**安全考虑：**

- **服务器端安全**：
  - Webhook URL验证和允许列表
  - 所有权验证/质询-响应机制
  - 网络控制和出口防火墙

- **客户端端安全**：
  - 验证A2A服务器身份
  - 验证签名和令牌
  - 防止重放攻击
  - 安全密钥管理和轮换

## 3. 代理发现机制

为了让AI代理使用A2A协议进行协作，它们首先需要找到彼此并了解其他代理提供的能力。

### 3.1 代理卡片的作用

代理卡片是一个JSON文档，充当A2A服务器的数字"名片"，包含：

- **身份信息**：`name`、`description`、`provider`
- **服务端点**：可以到达A2A服务的 `url`
- **A2A能力**：支持的协议功能（如 `streaming`、`pushNotifications`）
- **身份验证**：所需的身份验证方案
- **技能列表**：代理可以执行的特定任务或功能

### 3.2 发现策略

#### 众所周知的URI

**机制**：A2A服务器在标准化路径托管其代理卡片
- **标准路径**：`https://{agent-server-domain}/.well-known/agent-card.json`
- **优势**：简单、标准化，支持自动发现
- **适用场景**：公共代理或在特定域内广泛发现的代理

#### 精心策划的注册表

**机制**：中介服务维护代理卡片集合
- **过程**：
  1. A2A服务器向注册表注册其代理卡片
  2. 客户端查询注册表API搜索匹配代理
  3. 注册表返回匹配的代理卡片列表
- **优势**：
  - 集中管理和策划
  - 基于功能能力的发现
  - 访问控制和信任机制
- **考虑**：需要额外的注册表服务

#### 直接配置/私有发现

**机制**：客户端直接配置代理卡片信息
- **方式**：硬编码、配置文件、环境变量、专有API端点
- **优势**：对已知、静态关系简单有效
- **考虑**：动态发现灵活性较低

### 3.3 代理卡片安全

代理卡片可能包含敏感信息，需要适当保护：

**保护机制：**
- **端点访问控制**：使用mTLS、网络限制、标准HTTP身份验证
- **注册表的选择性披露**：根据客户端身份返回不同级别的详细信息
- **最佳实践**：避免在代理卡片中存储明文秘密

## 4. 技术集成最佳实践

### 4.1 任务状态管理

- 为有状态任务实现持久的 `TaskStore`
- 合理处理任务超时和清理
- 提供清晰的错误处理和状态转换

### 4.2 流式传输优化

- 实现适当的背压控制
- 处理网络中断和重连机制
- 合理分块大工件以提高传输效率

### 4.3 安全实施

- 使用强身份验证机制（OAuth 2.0、mTLS等）
- 实施请求验证和速率限制
- 定期轮换密钥和令牌
- 监控和审计所有代理间通信

### 4.4 可观测性

- 实施详细的日志记录和监控
- 跟踪任务执行指标
- 提供健康检查端点
- 实现分布式追踪

这些技术实现细节确保了A2A协议能够支持从简单的请求-响应交互到复杂的长时间运行任务的各种用例，同时维护安全性、可靠性和可扩展性。
